# secure-browser-agent

Safe local wrapper around `agent-browser` for authenticated browser analysis and scraping.

## Position

This tool is intentionally a thin orchestration layer:

- `agent-browser`: default execution engine for fast CDP control, compact accessibility snapshots, profile/state persistence, and low token usage.
- Playwright: compatibility layer for tests, richer automation APIs, and future remote CDP targets.
- Lightpanda: candidate fast crawler/rendering backend for non-authenticated or low-risk dynamic pages.
- Selenium: compatibility option for WebDriver/BiDi ecosystems, not the default for agent-first scraping.

## Safety Defaults

- URL allowlist is required: edit `config/example-policy.json` or set `SBA_POLICY`.
- Browser state is stored under `profiles/`, which is gitignored.
- `--profile` is the default persistence mode. `--state-only` is available for Playwright-style storage-state workflows, but it is not combined with `--profile`.
- Do not attach to the normal Chrome profile. Use a dedicated profile per target service.
- DOM, network bodies, and page text are untrusted data. They are never treated as instructions.
- Secrets should enter through existing browser login or a vault-backed workflow, not command-line arguments.
- CDP launch readiness waits up to 30 seconds by default. Set `SBA_CDP_LAUNCH_TIMEOUT_MS` higher on a loaded machine before treating `DevToolsActivePort` startup delays as browser failure.

If target approval has a runnable next command, the runbook emits a separate `target-approval-resume-run` step that requires `target-approval-resume --run --operator-ok OK`; the plan step remains non-executing, and the checklist mirrors `agent_must_not_run_operator_resume_unattended`. It mirrors the operator-pack saved agent loop state with `agent_loop_step_saved_*`, `agent_loop_step_status_command`, `agent_loop_step_recommended_command`, `agent_next_*`, `agent_next_provider_*`, and `agent_next_provider_doctor_command` lines, so the human runbook and low-token agent handoff agree on whether to refresh the wrapper, run the monitor-only/provider-doctor step, or wait for operator approval. Pass `--monitor-timeout-ms 10000 --monitor-interval-ms 1000` to make the generated operator-pack refresh and agent-loop commands short probes. With `--write`, it writes the runbook under `runs/operator/` and refreshes the operator pack child status files, including `browser-route-latest.json`, `backend-matrix-latest.json`, `objective-proof-pipeline-latest.json`, `agent-proof-checklist-latest.json`, `agent-proof-closeout-latest.json`, and `background-proof-capture-status-latest.json`, so the Markdown checklist and machine-readable handoff stay aligned. For low-token polling, write JSON with `--write --out operator/operator-runbook-latest.json`; `operator-runbook-status --in operator/operator-runbook-latest.json --format compact` reads the saved JSON without recomputing the pack, rereads only the saved `objective-completion-audit` JSON to mirror current `objective_completion_audit_*` final-gate fields, and promotes its unattended-safe strict/refresh command to the top-level `agent_safe_next_*` lines when the saved runbook is fresh. `operator-runbook-watch --run --in operator/operator-runbook-latest.json --out operator/operator-runbook-latest.json --format compact` refreshes the runbook only when missing, stale, or parse-broken. The status/watch commands do not open Chrome, start capture, read browser storage, or return page content. MCP exposes the same surfaces as `sba_operator_runbook_status` and `sba_operator_runbook_watch`; `sba_operator_runbook_status` also accepts `objectiveCompletionAuditIn` and `objectiveCompletionAuditStaleAfterSeconds` when the saved final-gate file is not the default.

`objective-status` is read-only unless `--write` is passed. It combines the completion gate, current resume plan, saved `objective-resume` state, latest saved `handoff-run-latest.json` / `handoff-resume-latest.json` status, and wait-auth polling status when present. Use it as the shortest status surface during real external login handoffs; it prints `login-open`, `login-capture-wait`, `auth-check`, `handoff-resume`, `operator-ready-resume`, and `saved-resume-run` commands when a target pack is waiting on login. `--format compact` emits a low-token `key: value` summary for polling agents, including `human_action`, `automation_blocker`, `capture_blocked`, and `auth_state` so another agent can distinguish "complete login in the already-open dedicated browser" from "poll an active wait" without reading Markdown or mistaking local auth metadata for usable login. It also emits `handoff_auth_check_port_reachable` when a saved handoff has a CDP auth-check port; this is a local TCP reachability check only and does not open Chrome or read browser storage. `handoff-resume` is the preferred continuation command because it checks auth first, can open the dedicated login browser with `--open-login`, can wait in the background with `--wait-auth`, and captures only after login is proved. `auth-watch` is the safe side-channel polling command when another agent should watch login progress without starting capture. Compact output includes `recommended_opens_browser`, `recommended_starts_capture`, `recommended_requires_operator_approval`, `recommended_may_run_unattended`, `recommended_agent_run_command`, and `recommended_operator_approval_command`, so a polling agent can keep using `status` unattended while routing browser-opening or capture-capable `handoff-resume` commands to the operator approval lane. It also emits `agent_safe_next_*` and `agent_safe_next_command`; browser-opening or capture-capable recommendations fall back to the read-only `login-handoff-status` lane, while reachable monitor states use `target-auth-watch`. It also includes both `auth_watch_command` for watch-only polling and `handoff_resume_command` for the auth-first wait-and-capture lane. `login-capture-wait` opens the dedicated browser and keeps the CLI waiting for the secret-free auth-check before continuing to proof capture. `objective-status` marks wait-auth files with `Last updated`, `Age seconds`, `Stale`, and `Active wait`, so an old timeout file is not mistaken for a currently running login wait. It also emits `recommendedCommand` / `recommended_command`: if a login wait is already active it chooses `status`; otherwise, when a saved handoff exists, it chooses `handoff-resume`; older saved resume commands remain available as fallback. `--write` persists `runs/operator/objective-status-latest.json`.

`proof-gate-status` is read-only unless `--write` is passed. It combines `objective-status` and `target-proof-next --real-external` into one low-token proof gate view for agents that only need to know whether the real external authenticated proof is complete, which target is active, whether auth-check is still login-like, which artifacts are missing, and which command should run next. Use `--format compact` for `status`, `human_action`, `automation_blocker`, `capture_blocked`, `auth_check_ok`, `login_like`, `auth_state`, `auth_usable`, `profile_auth_metadata_only`, `auth_final_url`, `auth_title`, `handoff_auth_check_port`, `handoff_auth_check_port_reachable`, `missing_artifacts`, `next_artifact_action`, `next_artifact_blocker`, `artifact_command_covers`, `auth_watch_command`, `handoff_resume_command`, `target_approval_preflight_command`, `accepted_external_proofs`, `secret_values_read`, and `destructive_actions` lines. `handoff_auth_check_port_reachable` is a local TCP reachability check for the saved dedicated login browser CDP port; it does not open Chrome or read browser storage. `auth_watch_command` is safe for another agent to run when it should only monitor login progress without starting capture; `handoff_resume_command` is the auth-first wait-and-capture lane; `target_approval_preflight_command` is the read-only real-external guard before any operator-approved resume. Compact output also emits `agent_safe_next_*` and `agent_safe_next_command`: it chooses monitor-only auth watch when available, otherwise the read-only target approval preflight, so agents do not infer safety from the browser-opening `handoff_resume_command`. `next_artifact_action` tells another agent whether the current command should wait for login, run capture, write proof, or stop. `--write` persists `runs/operator/proof-gate-status-latest.json`, or a custom `runs/`-relative path with `--out`, so another agent can poll the exact same proof gate without recomputing context. `--strict` exits non-zero until an accepted real external proof exists.

`proof-gate-watch` is read-only except for its optional watch JSON under `runs/`. It polls `proof-gate-status` until the full real-external proof gate is complete or the timeout expires, but never starts capture, opens browsers, or reads browser secrets. Use `--format compact` for low-token background monitoring during operator login handoff, and `--write --out operator/proof-gate-watch-status.json` when another agent should poll the latest `status`, `last_gate_status`, auth-check state, artifact count, and next command from disk.

`login-handoff-status` is the shortest read-only login handoff view. It wraps the proof gate into operator-safe decisions: whether login is still required, whether the dedicated browser CDP port is reachable, whether monitor-only polling is safe, whether capture is blocked until auth, and the exact `target-auth-watch` / `target-handoff-resume` commands. It never opens Chrome, starts capture, reads cookies, or reads secret values; use it for low-token continuations while the operator is completing login. Compact output emits `agent_safe_next_*` and `agent_safe_next_command`: it chooses monitor-only `target-auth-watch` when the saved handoff port is reachable, otherwise it mirrors the proof gate's read-only safe next action, so agents do not run `auth_first_resume_command` without operator approval.

`background-monitor-plan` is read-only and does not start the monitor itself. It emits a copy-pastable `nohup` command that runs `proof-gate-watch --write` in the background, writes a PID and log under `runs/operator/`, and keeps polling state in `runs/operator/background-proof-gate-watch-status.json`. The suggested command is monitor-only: it does not open browsers, start proof capture, read cookies, or read secret values.

`background-proof-capture-plan` is read-only and does not start anything. It packages the auth monitor command, the operator login command, and a no-open background `target-handoff-resume --run --wait-auth` command for the existing dedicated login browser. The no-open variant removes `--open-login`, adds bounded `--wait-auth-timeout-ms` / `--wait-auth-interval-ms`, writes log/PID paths under `runs/operator/`, and starts proof capture only after the target auth-check passes. The operator must open or finish login separately; the plan never reads cookies, browser storage, page rows, or secret values.

`background-proof-capture-status` is read-only and does not start or stop jobs. It reads the background monitor/capture PID files, sanitized log summaries, and target output status files such as `auth-watch-status.json`, `handoff-resume-wait-auth-status.json`, and `handoff-resume-latest.json`. Compact output reports whether monitor/capture jobs are running, whether auth-watch or wait-auth status exists, the direct `no_open_wait_capture_command`, the detached `background_no_open_wait_capture_command`, and which audit commands to run next, without opening browsers, reading cookies, or dumping page rows. It also emits `agent_safe_next_*` with `background-proof-capture-plan` as the unattended-safe read-only follow-up, while the no-open capture commands remain operator-approved execution lanes.

`background-proof-capture-start` is permission-gated. Normal mode is plan-only and never starts a process. With `--run --operator-ok OK`, `--mode monitor` starts the monitor-only auth watch in the background, while `--mode capture` starts the no-open wait-auth capture command and refuses commands that include `--open-login`. Pass `--timeout-ms` / `--interval-ms` to preserve the capture wait-auth bounds in both the approved command and foreground command; pass `--monitor-timeout-ms` / `--monitor-interval-ms` to preserve short monitor-only auth-watch probes. It writes PID/log files under `runs/operator/`, avoids duplicate live PID starts unless `--force` is passed, and still never reads cookies, browser storage, page rows, or secret values.

`objective-resume` uses the same selector but returns a runnable resume plan. Normal mode is read-only; `--run` executes only the structured primary command chosen by `objective-next`, and any command that may open a browser or start capture is blocked until the operator also passes `--operator-ok OK`. If the current primary action opens a login lane, credential entry stays in the dedicated headed browser. When a saved handoff exists, the primary action is `target-handoff-resume --run --open-login --wait-auth`, which performs its own auth check, opens the login browser if needed, waits for login, and returns `waiting-for-login` instead of starting capture too early; it still requires `--operator-ok OK` because it may open Chrome and later capture after auth is proved. Older `target-handoff-run` handoffs are still supported behind `--operator-ready` for compatibility, and `--operator-ready` remains a login-complete assertion, not an execution approval. If you want the CLI to open the browser and wait for login instead, use `objective-resume --run --operator-ok OK --manual-candidate login-capture-wait`. For short agent probes, add `--wait-auth-timeout-ms 10000 --wait-auth-interval-ms 1000`; those probe runs write `operator-handoff-probe.json`, `wait-auth-status-probe.json`, and, when `--write` is used without `--out`, `runs/operator/objective-resume-probe-latest.json`, so the normal `operator-handoff.json`, `wait-auth-status.json`, and `objective-resume-latest.json` keep the full operator wait. Use `--format compact` for low-token agent loops that need action, `operator_ok_required`, `operator_ok_accepted`, `planned_command_opens_browser`, `planned_command_starts_capture`, `opens_browser_now`, `starts_capture_now`, `human_action`, `automation_blocker`, `capture_blocked`, `next_artifact_action`, readiness, preflight, result, and command fields without the full Markdown handoff. For operator handoff, omit the short wait flags and the login lane uses the normal five-minute wait. Pass `--write` to persist the normal resume state to `runs/operator/objective-resume-latest.json`, including blocked/planned states, for low-token handoff. The handoff resume writes `handoff-resume-latest.json` under the target pack output directory.

`reap-owned` defaults to dry-run. It only targets `agent-browser` sessions and Chrome processes using this tool's `profiles/` directory.

## Authenticated Profile Flow

1. Run `scaffold-target` with exact `--origin` values for the target service.
2. Run `login` with a dedicated profile name.
3. Finish login manually in the opened browser.
4. Reuse that profile with `snapshot` or `extract`.
5. Delete `profiles/<target>` when the target project ends or within 30 days of last use.

`scaffold-target` writes a target pack under `runs/target-packs/<name>/` with `policy.json`, `recipes/diagnose.json`, `recipes/observe.json`, `recipes/inspect.json`, `recipes/analyze.json`, `recipes/operate.json`, `recipes/screenshot.json`, `recipes/crawl.json`, `recipes/outline.json`, `recipes/scrape-links.json`, `recipes/search.json`, and a command README. It does not write credentials; login still happens only in the dedicated browser profile.

Use `target-login <pack>` to open the dedicated headed Chrome profile at the pack login URL. It reads `target.json` and `policy.json`, never accepts passwords, and leaves credentials only in the target profile. Its JSON output includes a `handoff` with the post-login `target-proof-capture <pack> --real-external --run --wait-auth --wait-auth-status-out wait-auth-status.json --format markdown` command when `--real-external` is supplied. Prefer `target-login-capture` for real external proof runs because it opens the browser and runs the waiting capture lane in one command.

Use `target-login-capture <pack> --real-external --wait-auth-status-out wait-auth-status.json --completion-audit --format markdown` when you want one command to open the login browser and then wait for login completion before automatically writing the target proof artifacts and final objective gate summary.

Use `target-status <pack>` before headless runs to confirm whether the dedicated profile has local state or cookie DB artifacts. It reports `likelyAuthenticated` from file metadata only, so a site can still require a fresh interactive login even when the profile has cookies.

Use `target-auth-check <pack> --write` after login and after starting the pack daemon to prove the pack page URL no longer looks like a login screen. Real external proof requires this stronger page-level check in addition to local profile metadata.

Use `target-permissions <pack> status|plan|set|apply` to persist and apply explicit Chrome site permissions to only the pack's dedicated profile. Supported permission names are `clipboard`, `downloads`, `notifications`, `geolocation`, `camera`, `microphone`, `popups`, and `sensors`. Origins must already be allowed by the pack policy; `apply` refuses to write while the pack daemon is running unless `--force` is supplied.

Use `target-daemon <pack> start|status|stop` to keep the pack's dedicated Chrome/CDP profile running in the background. `start` opens the pack page URL by default, and `target-run --daemon` or `target-scrape --daemon` reuses it.

Use `target-autostart <pack> plan|write|install|load|unload|status|remove` to generate and manage a macOS LaunchAgent for the pack's background daemon. `write` stores the plist under the target pack for review, `install` writes to `~/Library/LaunchAgents/`, `load` writes the install plist and runs `launchctl bootstrap gui/<uid> <plist>`, `status` runs `launchctl print gui/<uid>/<label>`, and `unload` runs `launchctl bootout gui/<uid>/<label>`. Activation is never done by `verify.sh`; run `load` only for a target you intend to keep running.

Use `target-add-url <pack> <url...>` to append allowed URLs to `recipes/crawl.json` without hand-editing JSON. It validates target policy origins and deduplicates normalized URLs.

After a pack exists, use `target-run <pack> diagnose|observe|inspect|analyze|operate|screenshot|crawl|crawl-links|outline|links|search`. It resolves the pack policy, profile, recipe, output path, CSV defaults, artifact paths, and manifest automatically. `analyze` is the target-pack page-structure alias for the same scraping-candidate inspection flow and writes `outputs/analyze.json`; `operate` writes `outputs/operate.json` with a pre-mutation observation and operation candidates before you add explicit fill/click steps or use the generated selector templates.

Use `target-run-status <pack> <recipe> --format compact` to read saved `outputs/*.json|csv` without returning page text or row data. It reports freshness, parse status, step types, result keys, row counts, and refresh/status commands, so another agent can decide whether to rerun `operate`, `analyze`, `search`, or `scrape` without loading the full artifact.

Use `target-operate-add <pack> fill|click|wait-for|wait|observe|inspect|extract` to append guarded steps to `recipes/operate.json` without hand-editing JSON. It validates any step URL against the target policy, redacts inline fill values from command output, and refuses likely password/token fields unless you use `--value-env ENV_NAME`. Then run `target-run <pack> operate --daemon` against the dedicated target profile.

Use `target-scrape <pack>` after login to analyze the pack page URL and write `outputs/scrape.csv` with the best suggested extractor. It accepts the same `--selector`, `--suggestion`, `--fields`, and `--daemon` options as `scrape-cdp`.

Use `target-doctor <pack>` before login or scheduled scraping. It checks policy origins, login URL, recipes, and search provider origins.

Use `target-audit <pack>` before authenticated or scheduled automation. It combines `target-doctor`, read-only profile metadata, permission status, daemon/autostart state, and a config-file secret scan that excludes browser profiles and outputs. It fails on unsafe policy scope, authenticated non-Chrome engines, normal Chrome profile use, or secret-like values in pack configuration.

For a real external target, save benchmark JSON before writing proof:

```bash
node src/cli.mjs target-proof-plan runs/target-packs/target-service --real-external --format markdown
node src/cli.mjs target-proof-plan runs/target-packs/target-service --real-external --strict --format json
node src/cli.mjs target-login-capture runs/target-packs/target-service --real-external --wait-auth-status-out wait-auth-status.json --completion-audit --format markdown
node src/cli.mjs target-auth-check runs/target-packs/target-service --write --status-out auth-check-status.json --daemon --strict --format compact
node src/cli.mjs target-auth-watch runs/target-packs/target-service --status-out auth-watch-status.json --timeout-ms 300000 --interval-ms 5000 --format compact
node src/cli.mjs target-proof-capture runs/target-packs/target-service --real-external --run --wait-auth --wait-auth-status-out wait-auth-status.json --completion-audit --format markdown
node src/cli.mjs target-benchmark runs/target-packs/target-service --write --out proof/target-benchmark.json --format json
node src/cli.mjs target-proof runs/target-packs/target-service --real-external --write --auth-check-file runs/target-packs/target-service/proof/auth-check.json --benchmark-file runs/target-packs/target-service/proof/target-benchmark.json
node src/cli.mjs readiness-audit --format markdown
```

## CDP Recipes

`analyze-cdp` is the default first probe for agents. It opens the page once and returns compact observation, scraping candidates, console diagnostics, network summary, and `suggestedExtractors` in one redacted JSON object.

`scrape-cdp` runs the same analysis and then extracts rows from the best suggested selector, or from `--selector` when provided. Use `--suggestion N` to choose a different `suggestedExtractors` entry, and `--out rows.csv --format csv` to write spreadsheet-ready rows.

`observe-cdp` returns a compact, low-token page view: title, URL, counts, top headings, limited links, forms, controls, and a short text sample. Use it before `outline-cdp` when an agent needs to decide the next action without reading a full page inventory.

`inspect-cdp` returns scraping candidates: repeated item selectors, table summaries, link counts, field hints, and sample rows. Use it before writing `extract-cdp` selectors or target recipes.

`wait-cdp` waits for a selector, text fragment, or URL fragment before returning. Use it after navigation or login redirects when dynamic pages need time to render.

`console-cdp` captures console log/error and uncaught exception summaries through CDP without dumping full page content. Use it to debug background automations and failed scrapes.

`screenshot-cdp` saves a PNG screenshot under `runs/` without bringing Chrome to the foreground. Use `--manifest` to write sidecar metadata with profile, policy, output path, and byte count.

Direct CDP commands use the regular macOS Google Chrome app by default (`/Applications/Google Chrome.app/...`) with a dedicated automation profile. Set `SBA_CHROME_PATH` to force a specific binary, or `SBA_PREFER_AGENT_BROWSER_CHROME=1` to prefer the agent-browser Chrome for Testing cache.

`cdp-start`, `cdp-status`, and `cdp-stop` manage a background Chrome/CDP process for one dedicated profile. Add `--daemon` to `outline-cdp`, `observe-cdp`, `analyze-cdp`, `scrape-cdp`, `inspect-cdp`, `extract-cdp`, `wait-cdp`, `console-cdp`, `screenshot-cdp`, `fill-cdp`, `click-cdp`, `network-cdp`, `search-cdp`, `run-cdp`, or `target-run` to reuse that process. The daemon metadata stores PID, local CDP port, profile path, headed/headless mode, and start time; it does not store cookies or page data.

`run-cdp` executes a small JSON workflow in one dedicated Chrome profile. Supported step types are `goto`, `search`, `search-status`, `fill`, `click`, `wait`, `wait-for`, `console`, `screenshot`, `extract`, `inspect`, `observe`, and `outline`. A recipe can use either `url` for a single page or `urls` for a multi-page sweep inside one browser session. A `search` step expands to provider navigation, outline, and `search-status`, so authenticated search sessions can be reused with `--profile` and provider challenges are machine-readable.

For transient local recipes, `run-cdp` retries once after a CDP socket close only when every recipe URL is local (`data:` or `about:blank`). External URLs, daemon runs, selector failures, and other page errors are not retried, so authenticated operations are not duplicated silently.

Example:

```json
{
  "url": "data:text/html,%3Ch1%3EBefore%3C/h1%3E",
  "steps": [
    { "type": "fill", "selector": "#q", "value": "hello" },
    { "type": "click", "selector": "#go" },
    { "type": "wait-for", "selector": "#result", "text": "hello", "timeoutMs": 2000 },
    { "type": "console", "as": "logs" },
    { "type": "screenshot", "out": "after-click.png", "as": "shot" },
    { "type": "extract", "selector": "#result", "fields": ["text"], "as": "result" },
    { "type": "outline", "as": "page" }
  ]
}
```
