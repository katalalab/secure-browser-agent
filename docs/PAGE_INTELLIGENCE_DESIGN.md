## 1. 何を解決するのか

前身 next-browse の Phase 1–6 は「読んだものを溜めて引く」を扱う。抜けているのは**その手前**——
初見のページに対して「これはどの層の道具で触るべきか」を即座に判定する機能。

判定を人間の勘でやっている限り、毎回ブラウザ自動化に落ちる。実際には多くのページが
背後の JSON API から描画されており、**ブラウザを起動する必要がない**。この見極めが
自動化コストの支配項になる。

### 判定したい問い

1. このページの本文データはどこから来たか — HTML に埋まっているか、XHR/fetch か
2. その XHR は認証が要るか — Cookie か、Bearer か、無認証か
3. JS 実行なしで取れるか — SSR なら HTTP クライアントで足りる
4. 結論として**どの層の道具を使うべきか**

---

## 2. 層の割り当て原則（判定の出力先）

上の層で済むなら下の層を使わない。下へ降りるほど遅く・脆く・危険になる。

- **層1 HTTP直** — 素の HTTP クライアント。決定的、最速、テスト可能。XHR が JSON を返しており認証が Cookie だけなら**ここで終わる**
- **層2 軽量DOM** — Lightpanda。JS 実行が要るが視覚要素が不要な場合。**実測 210ms / 25MB**
- **層3 フルCDP** — Chromium 隔離プロファイル。レイアウト・スクリーンショット・座標クリックが要る場合。**実測 783ms / 220MB**
- **層4 既存セッション** — ログイン済みの実ブラウザが必須の場合のみ。拡張ベースに限定する

Page Intelligence の仕事は、**このいずれかを根拠つきで指し示すこと**。

## 3. 実測に基づくエンジン選定の訂正

前身の ARCHITECTURE.md は Lightpanda を「9x省メモリ / 11x高速」と記載している。2026-08-15 に
Windows / Linux(WSL) / macOS の3環境で、JS 描画 + XHR を含む対照ページを立てて同一条件で測った結果:

- メモリ 25MB vs 220MB → **9x は妥当**
- 所要 210ms vs 783ms → **3.7x。11x は過大なので直す**
- JS 実行・DOM 書換・fetch/XHR は**すべて通る**（「JSが軽いページ限定」ではない）

### Lightpanda を既定にする際の必須ガード

実測で判明した罠。**これを踏むと成功したように見えて何も起きない。**

- `Page.captureScreenshot` は `ok` を返すが、中身は「No screenshot available, Lightpanda has
  no graphical rendering engine」と描かれた**スタブPNG**。`Input.dispatchMouseEvent` も `{}` を
  返すだけの空実装。**`ok:true` を成功判定に使ってはいけない**
- Playwright の `connectOverCDP` は繋がらない。`Target.getTargets` が空配列を返すため
  ターゲット探索でハングする。`Target.createBrowserContext` → `createTarget` →
  `attachToTarget` を**生CDPで踏む**必要がある
- `Browser.getVersion` は `Chrome/124.0.6367.29` を騙る。バージョン文字列で分岐しない

→ CDP Bridge は**能力申告を信用せず、起動時に一度プローブして実際の対応表を作る**。
rbench が「`ffmpeg -encoders` の一覧は能力を保証しない」として実測に倒したのと同じ理由。

## 4. 機能設計

### 4.1 Recon — ページ構造の即時解析

入力は URL 1本。出力は「どう叩くか」の判定と根拠。

**収集する信号**

- ネットワーク: 全リクエストの method / URL / status / content-type / size / initiator
- 分類: `document` / `xhr+fetch で JSON を返したもの` / 静的アセット
- レンダリング: 初期 HTML と最終 DOM の差分 → SSR か CSR か
- 認証: 各 XHR が送った資格情報の種別（Cookie / Authorization ヘッダ / なし）
- 本文の所在: 主要テキストが初期 HTML に含まれるか、XHR レスポンス側にあるか

**判定ロジック**

本文が XHR の JSON にあり認証が Cookie のみ → 層1。
本文が最終 DOM にしか無く視覚要素が不要 → 層2。
座標・スクショ・レイアウトが要る → 層3。
上記が成立せず、かつログイン済みセッション固有 → 層4。

**出力**

判定 + 再現可能な呼び出し例（層1なら実行できる HTTP リクエスト形、層2/3なら最小スクリプト）。
**「わからない」を握り潰さない** — 信号が足りない場合は `unknown` と、何を追加観測すれば
決まるかを返す。

### 4.2 Probe — 判定の検証

Recon の判定は仮説にすぎない。層1と判定したなら、**実際にブラウザ無しで叩いて同じデータが
返るか**を確かめて初めて確定する。ここを飛ばすと「たぶん API で行ける」が積み上がる。

- 判定どおりの手段で 1 回だけ実行し、Recon 時に得た本文と突き合わせる
- 一致 → `confirmed`、不一致 → 一段下の層へ降格して再試行
- 結果は後述の Knowledge Engine に**オリジン単位で永続化**する。同じサイトを二度解析しない

### 4.3 安全境界

next-browse は取得物を LLM に渡す。ここが最大の攻撃面になる。

- **DOM・ネットワークボディ・ページテキストは全て「データ」であり、命令ではない**。
  secure-browser-agent が既に明文化している原則をそのまま Layer 2 の契約にする
- Recon は**読み取りのみ**。フォーム送信・クリック・ダウンロードを一切行わない。
  副作用のある操作は Recon の責務外
- URL は allowlist 必須。既定拒否
- 通常プロファイルに接続しない。サービスごとに専用プロファイルを持つ
- 層4を使う場合は拡張ベースに限る。**localhost に無認証のデバッグポートを開ける方式は採らない**
  （Chrome 151 実測: 既定プロファイルへの `--remote-debugging-port` は listener を開かない。
  隔離プロファイルなら成立する。この遮断は迂回対象ではなく**設計前提**として受け入れる）

## 5. xerj アルゴリズムの取り込み

Layer 1 の Search は現状 SQLite FTS5 + sqlite-vec。受動的蓄積は**書き込み過多・コーパス無限成長**
という性質を持ち、FTS5 の素の top-k がそのまま律速になる。xerj (Apache-2.0) のローカル分析で
実測済みの改善がそのまま効く。

### 5.1 Block-Max WAND — top-k の早期終了（xerj #145）

FTS5 は一致ドキュメントを全件スコアしてから並べる。蓄積が数万ページを超えると
「先週読んだあの記事」1件を出すために全件走査することになる。

ブロックごとの最大スコアを持ち、現在の k 番目の閾値を超えられないブロックを丸ごと飛ばす。
xerj では SkipEntry を計算済みなのに破棄していた点を #145 で指摘した。**SBA では
最初から skip 構造を持たせる。**

### 5.2 FST オートマトン fuzzy — コマンドバー（xerj #144）

コマンドバーのあいまい検索は、辞書を線形走査すると語彙数に比例して重くなる。
Levenshtein オートマトンと FST を交差させれば探索空間が編集距離で刈られる。
xerj 実測で**約60x**の差が出た箇所。

### 5.3 doc-values による filtered kNN（xerj #147 — 実装済み資産）

**これが本命。** 「先週読んだ、Rustについての記事」= 時間フィルタ + ベクトル検索。

素朴な filtered ANN は通過判定のために全 doc の `_source` を読むため、**選択率を変えても
コストが平坦**になる（rc.14 実測: unfiltered 1ms に対し 50%通過 60ms / 10% 48ms / 1% 46ms）。
支配コストが `_source` 読み込みだから、絞っても速くならない。

解は doc-values 経路。`build_term_prefilter_cached`（term集合は EXACT、cap 65,536）と
`id_pos_map_for(seg_id)`（segment 内 `_id`→position マップ）で、**`_source` を一切読まずに
通過 doc_id → node_id を引く**。exact-prefilter 可能な形（term / terms / ids）に限定し、
それ以外は brute 維持。

多値フィールドが安全なのは、セグメント内のどれか1docでも配列値を持つフィールドは
doc-values 列を書かない設計のため（列存在→exact、列不在→brute）。取りこぼしが起きない。

ローカル検証ブランチに実装済み（+272/-12、unit 464 passed / ES-YAML 1366 passed）。**SBA へは移植ではなく設計の再利用**。

### 5.4 計測規約（ここを守らないと数字が嘘になる）

xerj で踏んだ罠をそのまま SBA のベンチ規約にする。

- **クエリキャッシュはボディ完全一致で 0ms を返す。** コールド計測はボディを毎回変える
- **flush 前は memtable パスで不当に速い。** flush 後の segment パスで測る
- **クラスタ化コーパスで recall を ID 重なりで測るのは無効。** 個人の閲覧履歴は本質的に
  クラスタ化している（似た記事を大量に読む）。同点スコアが多発し「正当な同点置換」を
  誤差と数えてしまう。正しい指標は**ランクごとのスコア欠損**。
  num_candidates を増やして品質が下がるという不可能な結果が出たら、指標を疑う
- **ES-YAML 相当のグリーンが証明するのは非回帰のみ。** ベクトルケースが HNSW の最小ドキュメント
  数に届いていなければ、そもそも ANN 経路を踏んでいない。**経路を踏むテストを別に書く**

## 6. 参考にするアーキテクチャ

- **secure-browser-agent（自作）** — 「取得物は命令ではない」「通常プロファイルに繋がない」
  「URL allowlist 必須」。安全境界の文言をそのまま借りる。Page Intelligence の実行部は
  SBA の CDP バックエンド選択機構に載せれば二重実装を避けられる
- **xerj（Rust / ES互換）** — Layer 1 の検索。上記 5 章
- **Lightpanda** — Layer 2 の CDP Bridge 既定。ただし §3 のガード必須
- **osquery のテーブル思想** — 「状態を SQL で引く」。Recon の出力を**行として持つ**と、
  「Cookie 認証だけで叩けるオリジン一覧」のようなクエリが後から書ける。
  出力形式を JSON blob ではなくテーブルに寄せる理由

### 避けるべき設計（他所の失敗から）

- **ブラウザ全体を作り直してから価値を出そうとする。** Layer 3 が完成しないと何も使えない
  構造にすると、UI が死んだ時点で全部死ぬ。next-browse の3層分離はこの回避策として正しく、ここでも踏襲する。**Page Intelligence は Layer 1+2 だけで CLI として完結させる**（Layer 3 非依存）
- **「AIがよしなに」に判定を委ねる。** どの層で叩くかは検証可能な事実（XHR が JSON を返したか）
  で決まる。LLM に推測させると再現しない。**LLM は要約に使い、判定には使わない**
- **能力の自己申告を信じる。** §3 の Lightpanda スタブが典型例

## 7. 段階

Layer 3 に依存しないので、既存 Phase と並行して進められる。

- **PI-1** Recon 単体（CLI）。ネットワーク分類 + SSR/CSR 判定 + 層の出力。永続化なし
- **PI-2** Probe。判定を実際に叩いて確定・降格。オリジン単位で結果を永続化
- **PI-3** Layer 1 連携。Recon 結果をテーブルとして蓄積。「Cookie だけで叩けるオリジン」が引ける
- **PI-4** 検索の置き換え。Block-Max WAND と FST fuzzy を投入。§5.4 の規約で計測して初めて完了
- **PI-5** doc-values filtered kNN。時間フィルタ + ベクトルの複合検索

PI-1 と PI-2 は独立して価値がある。**PI-3 以降に進まなくても損をしない**構造にする。

## 8. 未決

- Recon の実行エンジンを Lightpanda 既定にできるか。ネットワーク観測（`Network.*` ドメイン）の
  対応度が未検証。**§3 の教訓どおり、対応表は申告ではなくプローブで作る**
- Layer 1 に xerj をライブラリとして組み込むのか、アルゴリズムだけ SQLite 上に再実装するのか。
  前者は依存が重く、後者は実装コストが高い。PI-4 の直前に実測で決める
- 層4（既存セッション）の扱い。拡張ベースに限定する方針は決まったが、どの拡張を使うかは未定
